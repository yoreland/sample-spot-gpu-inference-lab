AWS Sample · Spot GPU · SGLang

低成本、一键、自助：用 AWS Spot GPU 打造短时推理测试环境

从浏览器里点一下，就在 Spot GPU 实例（H200 / B200 / B300）上拉起一套短时的 SGLang 推理栈，跑完临时测试、收到飞书（Lark）通知，用完即拆。无需 AWS 控制台操作， 无需漫长的容量预留等待，每一次实验都被记录下来供日后审计。

开源示例 / AWS Sample 许可证 MIT-0 配套博客代码库

这是什么

sample-spot-gpu-inference-lab 是一个「低成本、一键、自助」的 AWS Spot GPU 推理测试环境。它把一整套可运行的组件打包在一起：一个 AWS CDK 控制面、 一个 React 自助门户，以及四个 Python Lambda（api、poller、 deployer、orphan-cleaner），让你可以在自己的账户里复现这套模式。

业务用户在网页上选好实例类型和部署方案，点一次按钮，平台就会自动在 Spot GPU 实例上 通过 docker compose 部署 SGLang 推理服务，就绪后推送飞书通知。

本仓库是一篇博客文章的配套代码库，作为 AWS 示例（sample） 提供， 而不是受支持的产品（not a supported product），以 MIT-0 许可证发布。

为什么要做这个：三大痛点

需要在 GPU 上对大模型推理做基准或冒烟测试的团队，反复撞上同样的三堵墙。这个示例就是为了逐一击破它们。

痛点一：GPU 资源紧缺，而测试往往是短时、临时的需求

一次测试可能只需要 约 2 小时 的 GPU 时间，但一个 Capacity Block 容量预留通常意味着要 至少等 1 天。为了跑一个两小时的测试而等上一天，行不通。

→ 本方案使用 Spot GPU 容量，配合一个由 CDK 部署的 容量轮询器（poller），每分钟扫描各区域 / 可用区，一旦出现容量立即抢占启动 （快速路径，无需预留等待）。

痛点二：业务 / LOB 用户不熟悉 AWS，走中台工单又慢

把每一次实验都通过中台平台团队来走流程，会给本该自助完成的动作平添数天的延迟。

→ 本方案提供一个 React 自助 Web 门户：用户选好实例类型和部署方案， 点一次，平台就负责开机、部署并把结果回报给他，全程无需登录 AWS 控制台。

痛点三：反复试验需要留痕与审计

当同一个测试被跑了很多遍，你需要一份持久的记录：跑了什么、什么时候跑的、结果如何。

→ 本方案把每一次预约和状态变更都写入 DynamoDB，提供站内 History 历史页面，并把状态变更通知推送到 飞书（Lark）机器人，从而在产品内和聊天侧都留下可追溯的轨迹。

解决方案总览

三条主线分别对应上面的三个痛点：

  • Spot 容量 + 容量轮询器（快速路径）： 不去排队等 Capacity Block，而是用 Spot 容量加一个由 CDK 部署的轮询器， 每分钟扫描区域 / 可用区，容量一出现就抢占启动，没有预留等待。
  • React 自助门户（一键下单）： 业务用户在门户里选实例、选部署方案、一键提交，无需 AWS 技能。
  • DynamoDB 记录 + History 页面 + 飞书通知（留痕 / 审计）： 每次预约与状态变更持久化到 DynamoDB，站内 History 页面可查， 飞书（Lark）机器人在状态变更时推送消息。

架构走读

平台本身是一个 AWS CDK 栈：静态 SPA（S3 + CloudFront）、API（API Gateway + Lambda）、 DynamoDB 状态存储，以及 四个 Python Lambda（api、 poller、deployer、orphan-cleaner），由 EventBridge 定时器协调。Spot GPU 实例在 NVMe 上以 docker-compose 运行 SGLang 拓扑， 每一次状态变更都会扇出到飞书 webhook。

静态 SPA（S3 + CloudFront）

React/Vite 构建产物存放在 S3 桶中，前面由 CloudFront 分发。 用户直接访问 CloudFront 域名即可打开自助门户。

API（CloudFront /api/* → API Gateway + 授权器 + SSM）

CloudFront 把 /api/* 请求转发到 API Gateway （一个 CloudFront Function 将 /api/... 重写为 /<stage>/...）。 API Gateway 使用一个 Lambda 授权器 做 HTTP Basic 认证，校验的凭据来自 SSM SecureString 参数 /tpot-booking/basic-auth-credentials， 通过后再调用 api Lambda。仓库内不含任何凭据，需由运维方自行配置。

状态存储 — DynamoDB（3 张表）

表名作用
TpotBookingTable 预约（bookings）及其状态历史，带一个 instanceType-status-index GSI。
TpotNotificationConfigTable 飞书 webhook 配置（configId=global）。
TpotDeploymentPlanTable 部署方案（deployment plans）。

poller Lambda（EventBridge 每 1 分钟）

EventBridge 每分钟触发一次。它扫描处于 polling 状态的预约，并在第一个有容量的 区域 / 可用区里直接启动一个 Spot GPU 实例（带 Spot 市场选项的 RunInstances），可用区到子网的映射来自 SUBNET_MAP_CONFIG。 B300 / B200 / H200 走 直接启动（direct-launch） 路径（对于 B300 短暂的容量窗口， 先探测再启动太慢）。成功后它用条件写把预约翻转为 launching（避免重复启动）， 并异步调用 deployer。

deployer Lambda（两阶段）

阶段 1（deploy，由 poller 调用）： 等待 SSM 可达，然后下发一条长时运行的 SSM 命令，配置 NVMe RAID、下载模型，并对所选 SGLang 拓扑执行 docker compose pull + up。 阶段 2（check_progress，EventBridge 每 2 分钟）： 轮询 SSM 命令与服务健康端点， 随后把预约标记为 ready 或 failed。

orphan-cleaner Lambda（EventBridge 每 15 分钟）

每 15 分钟运行一次，回收那些已不再被任何活跃预约跟踪的、带标签的游离 Spot 实例，作为成本安全网。

通知（飞书 / Lark webhook + SNS 兜底）

每一个负责状态变更的 Lambda 都会推送到 飞书（Lark）webhook（并以 SNS 作为兜底主题）。webhook URL 在运行时从 DynamoDB 的通知配置表读取，而不是写死在代码里。

Compose 文件（7 个 SGLang 拓扑）

7 个 SGLang docker-compose-*.yaml 拓扑与 deployer 打包在一起，并部署到一个 S3 compose 桶； 它们可以在 S3 上更新而 无需重新部署（redeploy），详见 cdk/docs/UPDATE-COMPOSE.md。

成本与清理

Spot GPU 容量正是这套方案的核心价值：你只为短暂的测试窗口付费，而不必长期持有一个 Capacity Block 预留。 代价是 Spot 实例可能被中断，但这对临时测试是可以接受的。

用完后一定要拆环境——一个被遗忘的 GPU 实例非常烧钱。orphan-cleaner Lambda 会按计划回收游离实例作为安全网，但你仍应主动执行清理并核对。清理步骤见 docs/TEARDOWN.md。
